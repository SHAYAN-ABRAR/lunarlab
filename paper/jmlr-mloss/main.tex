\begin{abstract}%
\lunarlab{} is an open-source platform for auditing reward design in reinforcement learning. Around
Stable-Baselines3 training on Gymnasium's LunarLander-v3, it records the original reward, every added reward
term and the resulting training reward on each transition, and evaluates policies on the original reward
only. Checkpoints are selected on validation episodes, frozen as immutable, digest-checked copies and tested
once on disjoint seeds; interrupted runs continue from checkpoints that restore the algorithm state, including
the DQN replay buffer; runs record configuration hashes, seeds, software versions and source revisions.
Diagnostics independent of the reward under study expose reward exploitation, as a deliberately flawed hover
bonus demonstrates. The platform adds statistics across training seeds, counterfactual re-scoring, robustness and
preference-learning studies, a command-line interface, a Python API and a local web interface; an adapter layer
applies the same accounting to other Gymnasium environments.
493 automated tests (85.8\% statement and branch coverage) run on Linux and Windows. Published final tests
re-evaluate bit-identically on Windows; on Linux single episodes differ numerically while mean returns stay
within 1.6 and landing rates are unchanged. Reward accounting adds at most 4\% to training-loop time over plain
Stable-Baselines3. \lunarlab{} is released under the MIT License.
\end{abstract}

\section{Introduction}

Reward design is how practitioners steer reinforcement-learning agents, and a common way such projects fail: an
agent can drive a shaped or learned reward up while the intended task stays unsolved
\citep{amodei2016concrete,skalse2022gaming}. Potential-based shaping is the principled exception, leaving the
optimal policies unchanged \citep{ng1999shaping}. Telling these cases apart requires keeping the reward a policy
is trained on separate from the reward it is judged by, on every transition, and an evaluation protocol that
cannot leak test information into model selection; studies of experimental practice show how easily the latter
goes wrong \citep{henderson2018matters,agarwal2021precipice}.

Mature libraries provide reliable algorithms and training infrastructure
\citep{raffin2021sb3,huang2022cleanrl,raffin2020zoo}. By default they evaluate whatever reward the environment
wrappers return and leave held-out testing, checkpoint freezing and reward bookkeeping to the user (a sourced
comparison is in \url{docs/jmlr/COMPARISON_EVIDENCE.md}). A reward-learning library keeps the environment reward
beside the learned one \citep{gleave2022imitation}, and safety benchmarks score agents on a hidden performance
function \citep{leike2017gridworlds}. \lunarlab{} provides this bookkeeping as one tested workflow; it contributes
no new learning algorithm but makes reward-design experiments auditable and reproducible.

\section{Software Design}

\paragraph{Reward accounting.} A reward configuration is data with a strict schema and a content hash. One
Gymnasium wrapper computes, for every transition $(s,a,s')$, $r_{\mathrm{train}} = w\,r_{\mathrm{orig}} + \sum_k
F_k(s,a,s')$ with pure term functions shared by training, evaluation and re-scoring; it records the original,
per-term and training rewards, undiscounted and discounted, and never changes observations or termination flags.
Built-in terms include a time penalty, a deliberately flawed hover bonus and potential-based shaping
$F = \alpha(\gamma\Phi(s') - \Phi(s))$ with an absorbing terminal state and correct time-limit truncation;
property-based tests check that its discounted sum telescopes to the potential difference.

\paragraph{Evaluation protocol.} Evaluation always uses the unmodified environment reward. Validation and test
seeds are strict, distinct and disjoint, and the instantiated environment is checked against the protocol. The
checkpoint with the best validation return is selected, copied at the first final test to an immutable,
digest-checked artifact and never trained again; interrupted tests are retried on the same bytes, and a registry
of test exposure labels runs designed after an already-seen test as exploratory. A hover detector that does not
depend on the reward under study and a strict landing classifier expose reward exploitation.

\paragraph{Reproducibility infrastructure.} Each run records its configuration, reward and protocol hashes,
seeds, budgets in environment transitions, software versions and source revisions. Checkpoints are written
crash-safely with a SHA-256 manifest. An interrupted run continues from a checkpoint at a safe boundary that
restores networks, optimizer state and counters, for DQN also the replay buffer, target-network phase and
exploration schedule (validated numeric arrays, never unpickled); environments restart and random-number streams
are not restored, so continuation is not bit-identical to uninterrupted training.

\paragraph{Interfaces and extension.} The same core code serves a command-line interface, a Python API and a
local web interface (including a three-dimensional replay with per-step reward decomposition) under a local job
supervisor, without network services or accounts. Studies cover statistics across training seeds
\citep{agarwal2021precipice}, robustness to unseen physics, Optuna tuning on validation episodes only
\citep{akiba2019optuna} and rewards learned from preferences \citep{christiano2017preferences,bradley1952paired}.
A separate adapter layer applies the accounting and outcome audits to other Gymnasium environments
\citep{towers2024gymnasium}; its LunarLander adapter matches the main pipeline exactly in tests and a CartPole-v1
adapter demonstrates the contract, while training, the evaluation protocol and checkpointing remain specific to
LunarLander-v3.

\section{Quality, Comparison and an Example Study}

\paragraph{Software quality.} 493 tests (unit, integration, property-based and end-to-end, including a served
backend and parallel workers) give 85.8\% statement and branch coverage, and 15 browser flows exercise the web
interface; continuous integration runs the full suite on Linux and platform-sensitive tests on Windows (Python
3.12, 3.13). The test suite executes the tutorial, the API reference is generated from the code, and a
deterministic source archive is built and installed into a fresh environment.

\paragraph{Reproducibility.} One command (\texttt{reproduce-smoke}) runs the whole pipeline on a small run in a
temporary directory and verifies every provenance link (14 checks; a 15th trains twice and found identical
weights). Three published final tests ship as artifacts whose re-evaluation separates artifact integrity,
within-platform reproduction, cross-platform numerical agreement and conclusion stability (paired tests). All
300 episodes were bit-identical on the development machine and on Windows CI (Python 3.12, 3.13); on Linux none
was, with return differences up to 0.28 (PPO baseline) and 192 (DQN), yet mean returns within 1.6 and unchanged
pad-landing rates. Per-step traces locate the cause: given identical actions, the Linux simulator departs by about
one float32 unit after 2--24 steps and the trajectories part there, while the network's last-bit differences
change no action; a one-ulp perturbation on Windows likewise changes 93--94\% of the episodes, aggregates intact.

\paragraph{Runtime and memory.} Table~\ref{tab:overhead} compares plain Stable-Baselines3 PPO with the same model
trained through the reward accounting and through the full pipeline: the accounting costs at most a few percent
of training-loop time, and a complete run takes about a fifth longer, mostly for the validation episodes the
protocol requires.

\paragraph{Example: a reward exploited and exposed.} In the bundled study, PPO \citep{schulman2017ppo} was trained
for one million transitions with five seeds under four reward designs (DQN \citep{mnih2015dqn} and learned rewards
are also included). Figure~\ref{fig:accounting} shows what the accounting records: with the original reward the
training and original returns coincide, with potential-based shaping they differ by the shaping term, and with the
flawed hover bonus the training return reaches 746 (median over seeds) while the original return falls to $-50$;
in the frozen final tests those policies landed in none of 500 episodes. Time penalty and potential-based shaping
showed no clear improvement over the original reward (every probability-of-improvement interval contains 0.5).

\section{Availability, Limitations and Conclusion}

\lunarlab{} is available at \url{https://github.com/SHAYAN-ABRAR/lunarlab} under the MIT License (version
\TODO{release tag}) and installs from locked dependencies on Windows (Python~3.12, 3.13) and Linux
(Python~3.12) without proprietary dependencies; evidence for every number above is in the repository.

The main pipeline is specific to LunarLander-v3, the adapter layer has been demonstrated on CartPole-v1 only, and
the bundled study uses one training budget and three to five seeds per group. Bit-identical results hold within
one platform; across operating systems agreement is measured, not assumed. The experiments are a two-dimensional
simulation benchmark, not evidence about real rocket control. \lunarlab{} does not prevent reward hacking; it
measures and exposes it, turning reward-design experiments into results that others can audit and reproduce.
