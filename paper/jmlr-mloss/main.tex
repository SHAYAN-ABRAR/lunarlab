\begin{abstract}
Reward-design experiments need evidence that optimized reward reflects task performance. \lunarlab{} is an
MIT-licensed toolkit integrating reward accounting, policy evaluation and provenance. Built on Stable-Baselines3
and Gymnasium's LunarLander-v3, it decomposes rewards at each transition, stores episode totals, selects
checkpoints on validation seeds, and tests protected, digest-checked copies on separate seeds. Configuration
hashes and software records connect results to their artifacts. A CLI, Python API and local web application
expose the workflow; optional traces support inspection and re-scoring. Five PPO training seeds per design
illustrate its use: a flawed hover bonus yields high shaped returns but no strict landings in 500 test episodes.
Three distributed policies also expose a portability limit: Windows evaluations match selected summary fields,
whereas Linux trajectories diverge despite similar aggregates. The main workflow is LunarLander-specific;
a separate audit API is demonstrated on CartPole. The toolkit connects reward definitions, selected policies and recorded outcomes in an inspectable experimental workflow. Code: \url{https://github.com/SHAYAN-ABRAR/lunarlab}.
\end{abstract}

reinforcement learning, reward shaping, reward hacking, reproducibility, open-source software

\section{Introduction}
A policy can improve its training reward while failing the intended task, a problem studied as reward gaming
\citep{skalse2022gaming}. Auditing reward design requires separate accounts of original reward, modified
reward and behavioral outcomes, with evidence identifying the selected checkpoint and the observations used to select
it, complementing established concerns about RL evaluation and reproducibility
\citep{henderson2018matters,agarwal2021precipice}.

\lunarlab{} integrates reward accounting, validation-based selection, protected final-test artifacts, and
diagnostic replay. Researchers can inspect whether a reward modification improves task outcomes, which reward
components explain a trajectory, and whether re-evaluating the same policy preserves an observed failure.
This integration makes reward-design failures traceable from the reward specification to the tested policy.

\section{Workflow and Implementation}
\paragraph{Accounting and diagnostics.} The main pipeline uses Gymnasium's LunarLander-v3
\citep{towers2024gymnasium} and Stable-Baselines3 implementations of PPO and DQN \citep{raffin2021sb3}.
A wrapper computes $r_{\mathrm{train}}(s,a,s')=w\,r_{\mathrm{orig}}(s,a,s')+\sum_k F_k(s,a,s')$.
A validated, content-hashed configuration specifies the terms; shared pure functions compute them for
training, evaluation and trajectory re-scoring. Training persists episode totals for original reward,
training reward and each term; per-transition traces are optional. The wrapper preserves observations and
termination signals. LunarLander-specific diagnostics include a preset-independent hover detector and a strict
pad-landing classifier using position, attitude, contact and termination.

Built-in designs include a time penalty, a deliberately exploitable hover bonus and potential-based shaping
$F=\alpha(\gamma\Phi(s')-\Phi(s))$, which matches the learner's discount, uses zero terminal potential and
distinguishes time-limit truncation; property tests check telescoping. The policy-invariance theorem
\citep{ng1999shaping} does not guarantee better finite-budget learning.

\paragraph{Selection and provenance.} Validation and final-test seed lists are checked for duplicates and
overlap. Validation original return selects the checkpoint; final evaluation reports original return,
behavioral outcomes and re-scored training return. At first final testing, the selected checkpoint is copied
to a protected, SHA-256-verified artifact that interrupted tests reuse. A test-exposure registry marks derived
experiments as exploratory but cannot prevent investigator reuse of test insights. Records include
configuration/protocol hashes, transition budgets, software versions and source revisions.

Checkpoint continuation restores networks, optimizer state and counters, and for DQN also replay contents and
continuation metadata. The simulator and random-number streams are not restored, so continuation is stateful rather than
bit-identical to uninterrupted training. File integrity, numerical agreement and preservation of
scientific conclusions are separate questions.

\paragraph{Interfaces and extension.} A CLI, Python API and React/FastAPI application share the local research
core; replay (with a 3-D view of the 2-D simulation), re-scoring, robustness, tuning and preference
workflows need no hosted account. A separate \texttt{lunarlab.audit} API accepts reward terms and task adapters, with LunarLander consistency tests and a CartPole example; the main training,
checkpoint and web workflows remain LunarLander-specific.

\section{Relation to Existing Software and Engineering Evidence}
Stable-Baselines3 supplies monitoring, checkpoint tools and separate evaluation environments;
RL Baselines3 Zoo adds recipes, tuning and plotting \citep{raffin2020zoo}; CleanRL emphasizes inspectable
single-file algorithm implementations \citep{huang2022cleanrl}. The \texttt{imitation} library keeps original
rewards beside learned ones and implements preference learning \citep{gleave2022imitation}; rliable provides
robust aggregate statistics \citep{agarwal2021precipice}; AI Safety Gridworlds separates reward from
performance measures \citep{leike2017gridworlds}. \lunarlab{} builds on these tools to connect named reward
terms, checkpoint identity, held-out evaluation and diagnostics within a single LunarLander audit workflow.

\paragraph{Testing and packaging.} Validation records include 489 Python tests passed on Windows~11 (86\%
combined statement/branch coverage), 15 browser tests, and 189 release tests in a fresh source-archive
installation. Public CI at base revision \texttt{67440c6} also passed on Linux and Windows. Tests cover reward
identities, seed validation, freezing, continuation and interruption; tutorial, API and developer documentation
and deterministic archives support installation, extension and independent evaluation.

\section{Example Audit and Reproducibility Limits}
The primary demonstration trains PPO \citep{schulman2017ppo} with five seeds for each of four reward designs
(1,003,520 transitions per run), selects checkpoints on ten validation seeds and evaluates them on 100
disjoint test seeds per policy; Figure~\ref{fig:study} plots the committed per-policy summaries. The original
reward baseline has an interquartile-mean (IQM) original return of 268.6 and a 97.6\% strict landing rate.
The hover-bonus group has IQM $-33.1$, no strict landings in 500 episodes and 80\% timeouts; its mean
re-scored training return is 496.3, but its mean original return is $-23.5$. The discrepancy shows
exploitation of this design under the studied configuration, not a general detector-validation benchmark.

Time-penalty and potential-based shaping obtain IQMs 265.3 and 262.3; both probability of improvement
intervals include 0.5, so improvement is not established, and the bootstrap conditions on fixed evaluation seeds. The broader study has 38 policies and 3,800 final-test episodes; independent recomputation from the
exports matches all 38 policy means, landing/timeout rates and all ten group IQMs. Three packages ship with
the source; six learned-reward exports still need two original reward models before replay. DQN runs use a
shorter training budget; simulated preference labels and validation derive from original reward.

\paragraph{Re-evaluation evidence.} For a PPO baseline, a PPO hover-bonus policy and a DQN baseline, Windows CI
and recording-machine evaluations match all 300 episodes on five summary fields (length, original/training
return, environment outcome, strict landing). On Linux, summaries differ: mean returns by at most 1.52 and
individual original returns by up to 0.28, 11.9 and 192; strict landing rates stay at 96\%, 0\% and 29\%.
Holm-corrected paired tests detect no aggregate difference, which does not establish equivalence. Nine
open-loop traces show early simulator-state differences without greedy-action changes on recorded
observations, supporting a simulator-numerics explanation for these three policies and selected traces, not a
unique compiler cause.
